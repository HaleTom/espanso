# Findings

## 1. Correctness & functional completeness

### [NON-BLOCKING] XSync may attribute stale queued errors to the hotkey grab
- Type: Plausible risk
- Evidence: `espanso-detect/src/x11/native.cpp:256-259` (grab_error_code reset → XSync), `espanso-detect/src/x11/native.cpp:89-191` (all preceding ctrl_disp requests are reply-round-trips)
- Why it matters: `XSync` processes all pending errors on `ctrl_disp`; if any earlier no-reply request had queued an error, it would be mis-attributed to the hotkey grab, producing a false "conflict" warning.
- Recommendation: None needed now — every request before the grab loop (`XGetModifierMapping`, `XKeysymToKeycode`) returns a reply, forcing error processing before the grab window; only the reply-less `XGrabKey` calls can be pending at `XSync`. Leave as-is; document already in place.
- Confidence: Low

### Verified OK
- `RawHotKeyResult` (`espanso-detect/src/x11/mod.rs:97-103`) matches C `HotKeyResult` (`espanso-detect/src/x11/native.h:63-71`) field-for-field: success, key_code, state, error_code.
- No other consumer of the x11 `HotKeyResult` exists: win32/mac backends have their own `detect_register_hotkey` and structs (`espanso-detect/src/win32/native.cpp:374`, `espanso-detect/src/win32/mod.rs:103`); no cross-platform FFI drift.
- Mapping insertion is now unconditional (`espanso-detect/src/x11/mod.rs:195-201`): conflicted hotkeys keep working — preserves shipped behavior where the dead `res == BadAccess` check left `success = 1`.
- `XSync(disp, False)` does not discard queued events; correct choice (`espanso-detect/src/x11/native.cpp:257`).
