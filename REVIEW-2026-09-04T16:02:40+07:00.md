# Findings

## 1. Correctness & functional completeness

### [NON-BLOCKING] XSync may attribute stale queued errors to the hotkey grab
- Type: Plausible risk
- Evidence: `espanso-detect/src/x11/native.cpp:257-260` (grab_error_code reset → XSync), `espanso-detect/src/x11/native.cpp:89-191` (all preceding ctrl_disp requests are reply-round-trips)
- Why it matters: `XSync` processes all pending errors on `ctrl_disp`; a stale error from an earlier no-reply request would be mis-attributed to the hotkey grab, producing a false conflict warning.
- Recommendation: None needed — every request before the grab loop (`XGetModifierMapping`, `XKeysymToKeycode`) returns a reply, forcing error processing before the grab window; only the reply-less `XGrabKey` calls can be pending at `XSync`. Leave as-is.
- Confidence: Low

### [NON-BLOCKING] No automated regression test for the error path
- Type: Plausible risk
- Evidence: `espanso-detect/` has no C++/Rust test harness for the X11 registration path; repo has no TESTING.md.
- Why it matters: the fix's core claim (error_code set on BadAccess, mapping still inserted) is not CI-covered.
- Recommendation: requires an X server with a deliberately conflicting grab client; deferred to manual runtime verification (see "What I could not fully verify"). Not merge-blocking given no existing test infrastructure for this path.
- Confidence: High
